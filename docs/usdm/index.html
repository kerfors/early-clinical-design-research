USDM v4 and master protocols

On this page: What we have · Seen as an ICH M11 protocol · Method · What it showed: 21 breakpoints

The first round of this work asked whether USDM v4 can carry a master protocol. Both cases were built as USDM v4.0.0 JSON from their documents, step by step, and checked with the usdm-rdf validator. What USDM could not express is collected as a table of breakpoints. The design modules were built next to USDM for what it cannot carry. Each case's published file is also laid out as an ICH M11 protocol, to show where a master protocol does not fit M11: CPMP · REMAP-CAP (more below).

Not yet in either USDM file: the Schedule of Activities, a large part of USDM (ScheduleTimeline, Encounter, Activity, ScheduledActivityInstance). For CPMP, the 13 schedules (master and 12 ISAs) are extracted as data tables in soa2usdm-collections, ready for review and for mapping to USDM (more below). REMAP-CAP has no schedule tables.

Folder: usdm-master-protocol/ (its README records each step and decision). The USDM JSON files as built hold whole-document text and are not published; the notebooks re-create them from the source documents. The most complete file of each case is published without the section text (below). The counts below are the validator's own, read from the executed validation notebooks.

Seen as an ICH M11 protocol

Each published file laid out in the ICH M11 Template: every value is found by a query that follows the published HL7 and CDISC M11-to-USDM mappings, the method of usdm-one-graph. M11 describes one protocol. Where a master protocol's documents and versions give several values, each value says where it sits. The deep dive shows, for each mapping route, the condition and query, the mapping-log rows for the same object and attribute, and the breakpoints that name the same USDM element.

Method

  1. Read the documents. Table of contents, headings and section text from the PDF text layer; for CPMP, letter-spaced pages with word boundaries from OCR aligned line by line, and section numbers from the printed body heading. The cross-layer statements ("as specified in the Core Protocol", "will be specified in the DSA") by phrase rules, with direction and overridable defaults. 10_cpmp_page_text.py · 02_remapcap_structure.ipynb · 11_cpmp_structure.ipynb
  2. Map to USDM v4.0.0. Model and controlled terminology pinned from usdm-rdf (DDF-RA v4.0.0). A value only where the document states it; a required attribute with no source is left out and logged; one mapping-log row per decision, with evidence. Structure decisions by Kerstin, recorded in the README. 03_remapcap_usdm.ipynb · 12_cpmp_usdm.ipynb
  3. Validate. The usdm-rdf validator notebook, run unchanged: references, structural SHACL shapes, terminology. Every structural finding is checked against the absences the mapping logged. 04_run_usdm_rdf_validator.py
  4. Amendments. REMAP-CAP: Core 4.1 as a second study version, with a section-level diff of 4.0 and 4.1. CPMP: the Summary of Changes tables read cell by cell, with rules and redaction bars from the rendered page and every cell checked against OCR. 05_remapcap_amendment_breakpoints.ipynb · 13_cpmp_amendment_tables.py · 13_cpmp_amendments.ipynb
  5. Section text. One NarrativeContent per numbered section, in document order. 06_remapcap_narrative.ipynb
  6. Breakpoints. What the mapping logs marked not expressible, or possible only by copying or convention, collected with evidence. 05_remapcap_amendment_breakpoints.ipynb

Every notebook is generated by a script. The folder README records for each step where it was run and how its outputs were compared.
